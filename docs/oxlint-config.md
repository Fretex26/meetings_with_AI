# Change from `oxlint.json` to `.oxlintrc.json`

## What happened

`nest new` generated a file named `oxlint.json` under `apps/api/`. The project's lint script is:

```bash
oxlint src/ test/
```

That command does **not** pass `-c`, so Oxlint only looks for config under the names it documents: `.oxlintrc.json` or `oxlint.config.ts`. The filename `oxlint.json` is **not** loaded automatically.

On top of that, Nest's template `$schema` pointed at a Rust source file (`rules.rs`), not Oxlint's real JSON Schema. That did not break linting, but it left the editor without autocomplete or JSON validation.

## How it was verified

1. `"no-console": "error"` was added to the config, and a `console.log("x")` was placed in `src/main.ts`.
2. With the file named `oxlint.json`, `npm run lint` reported **0 errors** (the config was not applied).
3. After renaming to `.oxlintrc.json` and fixing `$schema`, the same rule failed on the `console.log`.

Conclusion: Oxlint needs a filename it discovers by default, not the one Nest generates today.

## File generated by Nest (before)

```json
{
  "$schema": "https://raw.githubusercontent.com/oxc-project/oxc/main/crates/oxc_linter/src/rules.rs",
  "rules": {
    "@typescript-eslint/no-explicit-any": "off",
    "@typescript-eslint/no-floating-promises": "warn"
  },
  "env": {
    "node": true
  }
}
```

Problems:

- Filename: `oxlint.json` (not auto-discovered).
- Invalid `$schema` for the IDE / JSON validation.

## Current file (after)

Path: `apps/api/.oxlintrc.json`

```json
{
  "$schema": "./node_modules/oxlint/configuration_schema.json",
  "rules": {
    "@typescript-eslint/no-explicit-any": "off",
    "@typescript-eslint/no-floating-promises": "warn"
  },
  "env": {
    "node": true
  }
}
```

Changes relative to the Nest template:

1. Renamed to `.oxlintrc.json`.
2. `$schema` set to `./node_modules/oxlint/configuration_schema.json`.

The rules and `env` stayed the same as what Nest generated.

## Note on `no-floating-promises`

The `@typescript-eslint/no-floating-promises` rule needs type-aware mode (`oxlint --type-aware` and the `oxlint-tsgolint` package). Nest's generated script does **not** enable that, so this rule does not run with `npm run lint` as written. Documented here for completeness; it is separate from the filename fix.
